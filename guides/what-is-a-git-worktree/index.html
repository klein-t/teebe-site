What is a git worktree?

The plain-English definition, why you'd want one, and the three commands to get started.

A git worktree is an extra working directory attached to a repository you already have. It gets its own checked-out files, its own branch and its own index, but it shares the same .git history, branches, stashes and remotes as your main checkout. In practice: two folders, two branches, one repository, and you can work in both at the same time without ever running git checkout. Git has shipped git worktree since version 2.5 in 2015, but it stayed niche until AI coding agents made "run several branches at once" an everyday need. If you'd rather see your worktrees than list them, teebe is a free macOS GUI built for exactly that.

The problem worktrees solve

A normal repository has one working directory, so only one branch can be checked out at a time. Every time you need another branch, you switch, and switching rewrites your files. Uncommitted work has to be stashed or committed half-finished first, and anything that depends on the files on disk, a node_modules folder, a build cache, a running dev server, has to be rebuilt or restarted. Do that four times a day and it adds up.

A worktree removes the "one directory" limit instead of working around it. Your feature branch stays checked out where it is. The hotfix, the pull request you're reviewing, or the agent session you just kicked off gets a directory of its own.

How a git worktree works

git worktree add creates a new directory and checks a branch out into it. Under the hood, git writes a small .git file in that directory that points back to the main repository. The object store, the commit history and all the refs stay in one place and are shared. Only the working files and an index are duplicated, which is why a worktree costs a fraction of a second clone and never needs its own git fetch.

One rule to remember: a branch can be checked out in only one worktree at a time. Each worktree therefore needs its own branch, or a detached HEAD. The full differences are in git worktree vs branch.

Benefits of git worktrees

  • No more branch switching. Your in-progress work never moves, so there's nothing to stash, nothing to commit early, and no chance of a messy stash pop later.
  • Each branch keeps its own build. Dependencies, compiled output and caches live per directory. Switching context is cd, not a rebuild.
  • Run things side by side. Tests on two branches at once, a dev server on main while you work on a feature, or a pull request checked out for review next to your own work.
  • Cheaper than a clone. One shared object store, one set of remotes to keep in sync, and commits made in any worktree are visible in all the others immediately.
  • One worktree per AI agent. Claude Code, Codex and Cursor all isolate parallel sessions in worktrees, so agents can't overwrite each other's files or yours.

The three commands you need

Create a worktree on a new branch, as a sibling folder of the repo:

git worktree add -b hotfix ../repo-hotfix

See every worktree of the repository, with its branch and HEAD:

git worktree list

Remove it when you're done (the branch stays until you delete it separately):

git worktree remove ../repo-hotfix

That covers most days. For creating from an existing or remote branch, moving, locking, pruning stale entries and the errors you'll hit, see the git worktree cheat sheet.

When a worktree is not the right tool

For a two-minute interruption on the branch you're already on, git stash is faster. If you want a completely separate copy with its own remote, a fork you're testing or a repository you never want sharing state with your main one, a second git clone is the honest answer. Everything in between, which is most parallel work on a single repository, is worktree territory.

Worktrees and AI coding agents

This is why worktrees went from a niche git feature to a daily one. claude --worktree starts a Claude Code session in a fresh worktree under .claude/worktrees/, the Codex app offers "Worktree" when you open a new chat, and Cursor gives each parallel agent its own isolated checkout. Our guides cover each: Claude Code worktrees, Codex worktrees, and Cursor worktrees and parallel agents.

The side effect is several directories on disk, each mid-change, and no easy way to see them together. teebe lists every worktree of every repo you add in one native macOS window, badges files the instant an agent touches them, and peeks any diff inline, so you can watch three sessions without three terminal tabs. Frequently asked questions

What is a git worktree in simple terms?

An extra working directory attached to a repository you already have. It has its own checked-out files, its own branch and its own index, but shares the same .git history, branches, stashes and remotes as your main checkout. It lets you work on two branches at the same time in two folders, without switching.

What is the benefit of git worktrees?

You stop switching branches. Each worktree keeps its own files, build output and dependencies on disk, so you can fix a bug on main, review a pull request, or run an AI coding agent on a second branch while your in-progress work stays exactly where it is. No stash, no rebuild, no half-done commits.

Is a git worktree the same as a clone?

No. A clone copies the entire object store and has its own remotes to keep in sync. A worktree shares one .git directory with the main checkout, so it costs only the working files and a small index, and commits made in one worktree are instantly visible in all the others.

How do I create a git worktree?

Run git worktree add -b <branch> <path> to create a new worktree on a new branch, for example git worktree add -b hotfix ../repo-hotfix. Use git worktree list to see all worktrees and git worktree remove <path> when you're done.

Can two worktrees check out the same branch?

No. Git allows a branch to be checked out in only one worktree at a time and refuses with fatal: 'branch' is already checked out. Give each worktree its own branch, or use a detached HEAD.
